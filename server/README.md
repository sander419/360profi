# 360PROFI · API склада и оборудования

Бэкенд под модуль оборудования: реестр, статусы, журнал по каждой единице,
дефекты, комплекты на выезд с предвыездной и постивентной отметкой.
Это уже не демо: данные лежат на сервере, вход по PIN, у ролей разные права.

## Стек и почему он такой

- **Node ≥ 22.18, TypeScript без сборки.** Node сам срезает типы, `tsc` в рантайме не нужен.
- **`node:sqlite`** — SQLite встроен в Node. Ни отдельной СУБД, ни нативной сборки
  (`better-sqlite3` требует компилятора, на Windows это отдельная боль). Вся база — один файл,
  бэкап = копия файла.
- **Fastify** — маршруты, валидация тел запросов по JSON-схеме, единый обработчик ошибок.
- Больше зависимостей нет: JWT и хеширование PIN собраны на `node:crypto`.

Когда одного файла перестанет хватать (несколько тысяч единиц и параллельная запись
с площадок), переезд на Postgres — это замена `src/db.ts` и диалекта в запросах.

## Запуск

```bash
npm install
npm run seed     # демо-данные и PIN-коды сотрудников (печатаются один раз)
npm run dev      # http://localhost:4000/api/v1, перезапуск при правках
npm test         # 31 тест: права, статусы, журнал, комплект, офлайн, снимки
```

Переменные окружения (все необязательные):

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `PORT` | `4000` | порт |
| `HOST` | `0.0.0.0` | интерфейс |
| `DB_PATH` | `server/data/360profi.db` | файл базы |
| `JWT_SECRET` | генерируется в `data/.jwt-secret` | подпись токенов |
| `CORS_ORIGIN` | `*` | список разрешённых источников через запятую |
| `PHOTO_DIR` | рядом с базой, `photos/` | где лежат снимки |
| `PUBLIC_APP_URL` | — | адрес приложения, подставляется в ссылки оповещений |
| `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` | — | слать оповещения в чат |
| `WEBHOOK_URL` | — | слать оповещения POST-запросом куда угодно |

## Роли

| Роль | Может |
| --- | --- |
| `tech` | всё по складу и выездам: заводить оборудование и проекты, создавать выезды, сканировать, менять статусы, заводить дефекты со снимком |
| `manager` | то же + видеть список сотрудников |
| `admin` | то же + заводить сотрудников и сбрасывать PIN |

Права намеренно широкие. В компании без процессов запрет «заводить оборудование
может только менеджер» означает, что склад не заведут вообще: железка появляется
в руках у техника. Кто что сделал, видно в журнале — этого достаточно, пока
не появится, что именно ограничивать.

Вход: телефон + PIN, в ответ токен на 30 дней (`Authorization: Bearer <token>`).
PIN хранится только как scrypt-хеш; после 10 неудачных попыток телефон блокируется на 15 минут.

## API

Все ручки под `/api/v1`, кроме `health` требуют токен.

| Метод | Путь | Кто | Что делает |
| --- | --- | --- | --- |
| GET | `/health` | все | живость + число единиц |
| POST | `/auth/login` | все | `{phone, pin}` → `{token, user}` |
| GET | `/auth/me` | вход | текущий пользователь |
| GET | `/equipment` | вход | список, фильтры `status`, `category`, `projectId`, `search` |
| GET | `/equipment/categories` | вход | категории для фильтра |
| GET | `/equipment/by-code/:code` | вход | **точка входа для QR-наклейки** |
| GET | `/equipment/:id` | вход | карточка |
| GET | `/equipment/:id/history` | вход | журнал по единице |
| POST | `/equipment` | вход | завести единицу (код сам станет `EQ-0007`) |
| PATCH | `/equipment/:id` | вход | правка полей |
| POST | `/equipment/:id/status` | вход | сменить статус |
| POST | `/equipment/:id/check` | вход | отметить проверку сегодняшним днём |
| POST | `/equipment/:id/defects` | вход | завести дефект (`id` можно задать с клиента) |
| POST | `/equipment/:id/photos` | вход | снимок поломки, base64 в JSON, до 4 МБ |
| GET | `/equipment/:id/photos` | вход | снимки по единице |
| GET | `/photos/:id?t=<токен>` | по токену | сам файл снимка |
| GET | `/defects` | вход | открытые дефекты (или `?status=`) |
| PATCH | `/defects/:id` | вход | `open` / `in_repair` / `closed` |
| GET | `/projects`, POST `/projects` | вход | проекты (код придумается сам: `P-2609-1`) |
| GET | `/users`, POST `/users`, POST `/users/:id/pin` | manager / admin | сотрудники и PIN |
| GET | `/kits`, `/kits/:id` | вход | комплекты и готовность в процентах |
| POST | `/kits` | вход | создать выезд (можно пустой) |
| POST | `/kits/:id/items`, DELETE `/kits/:id/items/:equipmentId` | вход | состав выезда |
| POST | `/kits/:id/checkout` | вход | отметка при погрузке; позиции нет в списке — добавится сама |
| POST | `/kits/:id/checkin-rest` | вход | принять весь остаток целыми одной кнопкой |
| POST | `/kits/:id/checkin` | вход | приём: `ok` / `damaged` / `missing` |

## Правила, зашитые в сервер

Их нельзя обойти из клиента — в этом смысл переноса на бэкенд:

- Любая смена статуса пишет строку в `equipment_events`: кто, когда, откуда, куда, по какому проекту.
  Журнал не редактируется и не удаляется.
- Статусы `project` и `reserved` без проекта не ставятся: «оборудование на выезде» без указания,
  на каком, — это потерянное оборудование.
- Оборудование в ремонте на выезд не выдаётся — даже сканом «на лету».
  Проверки идут до записи, чтобы отклонённая позиция не оседала в списке комплекта.
- Единицу, уже уехавшую на другой проект, нельзя погрузить во второй комплект.
- Возврат с пометкой `damaged` сам уводит единицу в ремонт и заводит дефект,
  `missing` — заводит блокирующий дефект. «Потом посмотрим» не остаётся в голове у техника.
- Позицию, отмеченную при погрузке, нельзя тихо убрать из комплекта.

## Работа без связи

Телефон на площадке копит отметки и досылает их пачкой. Сервер к этому готов:

- **`Idempotency-Key`** — заголовок с уникальным ключом операции. Первый запрос выполняется,
  его ответ сохраняется в таблице `operations`; повтор с тем же ключом получает сохранённый
  ответ и заголовок `Idempotent-Replay: true`, ничего не выполняя. Без этого потерянный
  ответ превращал бы одну проверку в две записи журнала. Записи старше 30 дней чистятся при старте.
- **`occurredAt`** в теле запроса — когда действие произошло на площадке. Попадает в
  `equipment_events.occurred_at`, а `created_at` остаётся временем записи на сервере:
  разрыв между ними и есть время без связи. Проверка, сделанная вчера, ставит вчерашнюю
  дату в `last_check_on`.
- Время с телефона проверяется: будущее дальше пяти минут и всё старше 60 дней отбрасывается,
  берётся серверное. Сбитые часы не должны портить журнал.
- **Поправка часов.** `/auth/login` и `/auth/me` возвращают `serverTime`; клиент запоминает
  разницу со своими часами и вычитает её из времени отметок. Телефон с неверной датой
  больше не пишет в журнал ерунду.
- **Идентификатор дефекта может прийти с клиента.** Это нужно, чтобы снимок, снятый без
  связи, сослался на дефект, которого на сервере ещё нет: в очереди они идут парой.
  Повтор того же идентификатора отклоняется с 409.

## Снимки

Приходят как `data:image/jpeg;base64,...` в JSON — тем же путём, что и остальные отметки,
поэтому умеют ждать связи в очереди клиента. Multipart для этого не годится.
Файлы лежат в `data/photos`, в базе только метаданные: бэкап базы остаётся быстрым.
Отдаются по ссылке с неугадываемым токеном — тег `<img>` не умеет передавать заголовок
авторизации. Клиент ужимает снимок до 1280 px и JPEG q0.7 (~150 КБ) прямо в браузере.

## Оповещения

Серьёзная поломка и пропажа оборудования уходят человеку сразу, а не ждут,
пока кто-то откроет список. Мелкие дефекты не шлются: оповещение на каждый скол
через неделю перестают читать.

Куда слать, решает окружение. Ничего не задано — оповещения выключены.

```bash
# в /etc/360profi.env
TELEGRAM_BOT_TOKEN=123456:AA...      # бот создаётся у @BotFather
TELEGRAM_CHAT_ID=-1001234567890      # id чата или группы
PUBLIC_APP_URL=https://sklad.example.ru/
```

Сообщение приходит с кодом, названием, описанием, автором и ссылкой на карточку.
Отправка не задерживает ответ сотруднику и не роняет запрос: отметка о поломке
важнее уведомления о ней.

## Схема данных

`users`, `projects`, `equipment`, `equipment_events`, `defects`, `kits`, `kit_items`,
`operations` (ключи идемпотентности), `photos` (метаданные снимков).
Миграции — нумерованные файлы в `migrations/`, версия хранится в `PRAGMA user_version`.
Правило: старые файлы не редактируются, изменения — новым файлом `002_*.sql`.

## Чего пока нет

- Уведомлений: чтобы менеджер узнал о новом дефекте, он должен открыть список.
- Управления комплектами и проектами из интерфейса — только через API.
- Аналитики по поломкам (какая модель чаще ломается, сколько стоил ремонт).
- Деплой описан в `deploy/`, но боевой хост поднимается отдельным решением.
