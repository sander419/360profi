# Эксплуатация: что делать, когда что-то случилось

Короткий runbook. Всё выполняется на сервере по ssh, каждая процедура — самостоятельная.

## Быстрая диагностика

```bash
curl -fsS https://<домен>/api/v1/health     # живо ли API и сколько единиц в базе
systemctl status 360profi-api               # состояние сервиса
journalctl -u 360profi-api -n 50 --no-pager # последние логи
systemctl list-timers 360profi-backup       # когда был и будет бэкап
```

## Приложение не открывается

1. `systemctl status nginx` — если лежит nginx, лежит и статика.
2. `systemctl restart 360profi-api` — сервис перезапускается за секунду, данные не теряются.
3. `journalctl -u 360profi-api -n 100` — смотрим причину. Частое: кончилось место на диске
   (`df -h`), тогда сначала чистим `/var/backups/360profi`.
4. Если API живо, а телефоны не пускают — проверьте, не истёк ли TLS-сертификат:
   `certbot certificates`.

## Люди не могут войти

| Симптом | Причина | Что делать |
| --- | --- | --- |
| «Неверный телефон или PIN» у одного | забыл PIN или опечатка в телефоне | перевыпустить PIN, проверить формат `+7900...` |
| «Слишком много попыток» | 10 неудач подряд | подождать 15 минут или перезапустить сервис |
| Не пускает всех разом | сменился `JWT_SECRET` | это отзывает все сессии; так и делают при утечке — люди просто входят заново |

## Восстановление из бэкапа

Бэкапы: `/var/backups/360profi/360profi_ГГГГ-ММ-ДД_ЧЧММ.db.gz`, ежедневно в 4:30, хранятся 30 дней.
Снимки поломок лежат отдельно, зеркалом в `/var/backups/360profi/photos` — база без них
будет ссылаться в пустоту, поэтому восстанавливать нужно обе части.

```bash
systemctl stop 360profi-api
cp /var/lib/360profi/360profi.db /var/lib/360profi/360profi.db.broken   # текущее состояние на всякий случай
gunzip -c /var/backups/360profi/360profi_2026-09-08_0430.db.gz > /var/lib/360profi/360profi.db
chown profi360:profi360 /var/lib/360profi/360profi.db
cp -ru /var/backups/360profi/photos/. /var/lib/360profi/photos/   # снимки
chown -R profi360:profi360 /var/lib/360profi
systemctl start 360profi-api
curl -fsS http://127.0.0.1:4000/api/v1/health
```

Потеряется всё, что внесли после снимка. Скажите людям, за какой период
нужно повторить отметки, — не молчите об этом.

## Обновление версии

```bash
sudo DOMAIN=<домен> bash /opt/360profi/deploy/install.sh
```

Скрипт подтягивает `main`, ставит зависимости, пересобирает фронт и перезапускает
сервис. Простой — несколько секунд. Откат: `git -C /opt/360profi checkout <старый коммит>`
и повторный запуск скрипта.

Миграции базы накатываются сами при старте, по возрастанию номера файла в `server/migrations`.
Правило: старые миграции не редактируются, изменения — новым файлом.

## Оповещения о поломках

Приходят в Telegram при серьёзном дефекте и при пропаже оборудования.
Подключение — три переменные в `/etc/360profi.env` (`TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID`, `PUBLIC_APP_URL`) и `systemctl restart 360profi-api`.

Перестали приходить — проверьте `journalctl -u 360profi-api | grep -i telegram`
и то, что бот не выкинут из группы. Сервер намеренно молчит об ошибках отправки:
недоступный мессенджер не должен мешать отмечать поломки.

## Кадровые изменения

- **Уволился:** деактивировать учётку. История его действий остаётся — она нужна
  для разбора старых инцидентов.
- **Потерял телефон:** сразу перевыпустить PIN. Старый токен на потерянном
  устройстве продолжает работать до 30 дней, поэтому при пропаже телефона
  с доступом к складу меняйте `JWT_SECRET` — это разлогинит всех и закроет вопрос.
- **Сменил роль:** поменять роль в базе, повторный вход не нужен только после
  обновления токена — проще попросить выйти и войти заново.

## Что считается нормой

- Сервис ест меньше 150 МБ памяти, лимит в юните — 512 МБ.
- База растёт медленно: тысяча единиц и год журнала — десятки мегабайт.
- Ответ API на списке склада — единицы миллисекунд.

Если база перевалит за пару сотен мегабайт или появятся жалобы на скорость —
это сигнал к переезду на Postgres, а не к покупке сервера побольше.

## Границы

Сервер, домен и деплой трогаются только по прямому решению — скрипты в `deploy/`
написаны так, чтобы их запуск был осознанным действием человека, а не побочным
эффектом чьей-то команды.
